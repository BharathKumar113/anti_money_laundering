--------------------------------------------------------------------------------

This project is a comprehensive, production-grade financial crime surveillance
and forensic analytics platform. It is engineered to monitor, evaluate, detect,
and investigate illicit financial activities in real-time, including:
- Smurfing & Structuring (breaking large deposits below mandatory $10,000 limits)
- Circular Layering & Round-Tripping (multi-hop money mule transaction loops)
- Account Draining & Rapid Velocity Depletion (illicit cashout surges)
- High-Risk Entity & Zero-Day Behavioral Anomalies

Traditional financial monitoring systems rely on rigid, static threshold rules
(e.g., flagging any transaction > $10,000), which suffers from two fatal flaws:
1. Catastrophic False Positive Rates (over 90% to 95%), overwhelming compliance
   officers with benign alerts and costing global institutions billions annually.
2. Inability to detect sophisticated multi-hop fraud networks, where funds are
   routed below statutory thresholds through distributed synthetic mule networks.

Our platform solves this crisis by deploying a 5-tier Defense-in-Depth hybrid
architecture that fuses:
1. Heuristic Rule Engine (Statutory compliance baseline)
2. Supervised Machine Learning (XGBoost Gradient Boosting Classifier)
3. Spatial Outlier Isolation (Scikit-Learn Isolation Forest)
4. Deep Neural Latent Bottleneck (PyTorch Multi-Layer Perceptron Autoencoder)
5. Topological Network Analytics (NetworkX Directed Multigraph Cycle Detection)

Coupled with Explainable AI (SHAP attributions), a dynamic runtime plugin
management system, an immutable audit ledger, and an interactive pure HTML/CSS/JS
engineering diagrams engine with real-time transaction simulation, this platform
provides end-to-end operational readiness for modern tier-1 financial institutions.

2. THE REAL-WORLD AML CRISIS & THE THREE STAGES OF LAUNDERING
================================================================================
Money laundering accounts for 2% to 5% of global GDP ($800 billion to $2 trillion)
annually according to the United Nations Office on Drugs and Crime (UNODC).
Financial institutions face severe regulatory penalties (FinCEN, FATF, FCA, RBI)
if they fail to maintain effective Bank Secrecy Act (BSA) compliance programs.

The Three Core Typologies of Money Laundering Targeted:
1. Placement:
   - Introducing illicit "dirty" cash into the financial ecosystem.
   - Tactics: Structuring ("smurfing") transactions into sub-$10,000 deposits,
     using shell companies, or utilizing crypto ATM on-ramps.
   - Platform Countermeasure: Deterministic BSA rules combined with 1-hour,
     24-hour, and 7-day rolling velocity accumulators that identify deposit
     frequency bursts regardless of single transaction sizes.

2. Layering:
   - Obscuring the audit trail and severing the link between funds and crime.
   - Tactics: Rapid multi-hop wires, circular transfers across shell entities,
     and complex web transactions through intermediary mule accounts.
   - Platform Countermeasure: NetworkX topological directed graph analytics
     detecting cycles (lengths 2 to 5 hops) and degree anomalies in < 5ms, paired
     with supervised XGBoost decision trees evaluating non-linear transfer traits.

3. Integration:
   - Re-introducing laundered wealth into the mainstream economy as ostensibly
     legitimate assets (real estate, luxury acquisitions, commercial ventures).
   - Platform Countermeasure: Deep PyTorch Autoencoder reconstruction anomaly
     scoring and Isolation Forest spatial partitioning that flag structural
     deviations in account activity compared to historical baseline profiles.

3. SYSTEM ARCHITECTURE (6-LAYER HIGH-THROUGHPUT DESIGN)
================================================================================
The platform is organized into six clean, decoupled architectural layers designed
for sub-15ms processing latency and zero-downtime extensibility:

[ Layer 1: Client & Ingestion Layer ]
  - React 18 Single Page Application (SPA): Built with Vite, Chart.js KPI boards,
    and Vis-Network dynamic graph canvas for interactive forensic investigations.
  - Core Banking Rails: Ingests real-time payment streams (SWIFT, Fedwire, ACH).
  - Bulk PaySim Batch Ingestion: Asynchronous CSV processor handling large files.
  - Interactive Diagrams Hub: Native HTML/CSS/JS dashboard mounted at /diagrams/.
  - Swagger OpenAPI Interface: Auto-generated interactive REST tests at /docs.

[ Layer 2: API Gateway & Security Layer ]
  - FastAPI ASGI Framework: Asynchronous non-blocking event-driven request loop.
  - Pydantic v2 Schema Enforcement: Strict runtime payload validation.
  - Security & Auth: Bearer JWT validation, rate limiting, and CORS headers.
  - Observability Middleware: Precise microsecond request timing headers
    (`X-Process-Time-Ms`) and structured diagnostic logging.

[ Layer 3: Feature Engineering & State Caching ]
  - PaySim Vectorizer: Computes 18-dimensional feature vectors in under 4ms.
  - Accounting Discrepancy Formulations: Real-time delta balance checks.
  - Velocity Window Tracker: In-memory sliding time-window transaction counters.

[ Layer 4: 5-Tier Hybrid Detection Ensemble ]
  - Concurrently evaluates every transaction across 5 independent engines:
    1. Heuristic Rule Engine (0.8 ms)
    2. XGBoost Gradient Boosting Classifier (3.2 ms)
    3. Isolation Forest Outlier Detector (2.8 ms)
    4. PyTorch Deep Autoencoder Neural Network (5.1 ms)
    5. NetworkX Graph Cycle & Mule Ring Analyzer (4.5 ms)

[ Layer 5: Meta-Classifier Ensemble & Decisioning ]
  - Dynamic Plugin Manager: Dynamically enables, disables, and reweights models.
  - Platt Scaling Calibration: Maps heterogeneous distance scores into a clean,
    well-calibrated 0.0 to 1.0 (or 0–100) risk probability.
  - Decision Gate (Threshold >= 0.70): Triggers automated SAR generation,
    account hold directives, and webhook alert dispatches.

[ Layer 6: Persistence, Forensics & Audit Ledger ]
  - SQLAlchemy 2.0 ORM: Connected to SQLite (local development) and PostgreSQL
    (production cloud environments).
  - Relational Schema: `transactions`, `alerts`, and `audit_logs` tables.
  - Cryptographic Audit Trail: Full immutable record of all model predictions,
    feature inputs, SHAP attributions, and human officer dispositions.

4. DATA FLOW SPECIFICATIONS (DFD LEVELS 0, 1 & 2)
================================================================================
The platform data flow is structured across three rigorous decomposition levels:

* DFD Level 0 (Macro Context Boundary Diagram):
  - External Entities:
    1. Core Banking Rails (Sends raw transaction streams; receives hold notices)
    2. AML Compliance Analyst (Receives prioritized alerts; submits dispositions)
    3. FinCEN / Regulatory Gateway (Receives automated electronic SAR filings)
    4. Notification Gateway (Receives real-time pager/webhook alert pushes)
  - Central Process: Process 0.0 (AI Anti-Money Laundering Platform).

* DFD Level 1 (Functional Subsystem Architecture):
  - Process 1.0: Ingestion, Auth & Schema Validation
  - Process 2.0: Hybrid Multi-Model Ensemble Scoring
  - Process 3.0: Graph Network Forensics & Mule Ring Analysis
  - Process 4.0: Alert Triage & Compliance Case Management
  - Process 5.0: Regulatory SAR Formatting & Audit Logging
  - Data Stores:
    - D1: Transaction Ledger Store (Immutable raw records & balances)
    - D2: Entity Feature Cache (Rolling velocities, historical metrics)
    - D3: AML Alerts & Investigation Cases (Scores, notes, dispositions)

* DFD Level 2 (Real-Time Ingestion & 5-Model Pipeline):
  1. Raw JSON transaction arrives via POST `/api/v1/transactions`.
  2. Sub-Process 2.1 parses payload with Pydantic v2 and checks balance sanity.
  3. Feature Vectorizer extracts 18 features (deltas, ratios, velocity logs).
  4. Fan-Out: The 18-dim vector is broadcast concurrently to all 5 engines:
     - Engine 1: Evaluates deterministic rule thresholds ($10k, structuring).
     - Engine 2: XGBoost computes supervised tree fraud probability.
     - Engine 3: Isolation Forest computes spatial hyper-plane anomaly score.
     - Engine 4: Autoencoder computes latent bottleneck reconstruction MSE.
     - Engine 5: NetworkX traverses sender/receiver graph for cycles.
  5. Sub-Process 2.7 (Meta-Ensemble) computes weighted calibrated risk score.
  6. Decision Gate: If score >= 0.70 (70%), an automatic SAR alert is generated.
  7. Ledger Commit: Transaction and alert are committed to SQLite/PostgreSQL.
  8. Response: Returns HTTP 201 with risk score and explainability in < 15ms.

     * `GraphService`: Exposes multi-hop neighbor search and cycle detection.

2. UML Sequence Diagram (Real-Time Ingestion Flow):
   - Sequence: Client -> Gateway -> TransactionEngine -> FeatureStore ->
     5 ML Plugins -> MetaEnsemble -> Database Ledger -> Notification Dispatcher.
   - Fully asynchronous non-blocking flow completing end-to-end in < 15ms.

   - Primary Actors:
     * AML Compliance Analyst: Inspect alert queue, explore Vis-network mule
       subgraphs, assign risk priorities, file electronic SARs, close false positives.

6. THE 5-ENGINE DETECTION ENSEMBLE (WHAT, WHY & HOW)
================================================================================
No single machine learning model can solve all financial crime vectors. Supervised
models only detect known historical patterns; unsupervised models catch zero-day
anomalies but suffer higher variance; graph algorithms reveal structural rings
that tabular models cannot perceive; and rule engines are legally required.

Our platform blends all five:

1. Supervised XGBoost Classifier (`xgb_aml.joblib`):
   - Algorithm: Extreme Gradient Boosted Decision Trees.
   - Why Chosen: Industry benchmark for tabular financial transactions.
   - Training Source: Trained on high-risk PaySim transaction classes (TRANSFER
     and CASH_OUT) using class-frequency weighting (`scale_pos_weight`).
   - What It Detects: Known illicit transfer signatures, rapid balance depletion,
     and suspicious origin-to-destination ratio combinations.
   - Ensemble Weight: 1.0 (Highest baseline weight).

2. Unsupervised Isolation Forest (`isolation_forest.joblib`):
   - Algorithm: Spatial partition trees isolating anomalies in feature space.
   - Why Chosen: Does not require historical fraud labels. Outlier points require
     substantially fewer recursive splits to isolate than normal points.
   - What It Detects: Structural outliers, unexpected transaction spikes, and
     unusual behavioral novelties.
   - Ensemble Weight: 0.85.

3. Unsupervised PyTorch Deep Autoencoder (`autoencoder.joblib`):
   - Algorithm: Deep Multi-Layer Perceptron Autoencoder with latent bottleneck
     (18 -> 12 -> 6 -> 2 -> 6 -> 12 -> 18).
   - Why Chosen: Compresses transaction dimensions into a 2-dimensional latent
     representation, then reconstructs them. Trained exclusively on normal
     banking transactions, so it fails to reconstruct novel fraud patterns.
   - What It Detects: High Mean Squared Error (MSE) between input features and
     reconstructed output signals zero-day structural divergence.
   - Ensemble Weight: 0.80.

4. NetworkX Graph Analytics (`graph_ring_plugin.py`):
   - Algorithm: In-memory Directed Multigraph Cycle Detection & Centrality.
   - Why Chosen: Tabular models cannot see multi-transaction relationships.
     Criminals use layering chains (A -> B -> C -> A) to disguise illicit origin.
   - What It Detects: Circular round-tripping loops (lengths 2 to 5 hops),
     money mule fan-in / fan-out clusters, and rapid hop routing.
   - Ensemble Weight: 0.90.

5. Heuristic Compliance Rule Engine (`rule_based_plugin.py`):
   - Algorithm: Deterministic Threshold Logic.
   - Why Chosen: Statutory mandates (FinCEN BSA, FATF, RBI) legally require
     deterministic reporting regardless of AI confidence.
   - What It Detects: Hard currency thresholds (>= $10,000 / ₹2,00,000), total
     origin account emptying, and unverified mule destination accounts.
   - Ensemble Weight: 0.50.

7. MATHEMATICAL FORMULATION & ENSEMBLE SCORING
================================================================================
1. Weighted Blending:
   The composite risk score R_raw is computed as the normalized dot product of
   active plugin scores S_i and their configured weights W_i:

     R_raw = ( ∑_{i=1}^N W_i * S_i ) / ( ∑_{i=1}^N W_i )

2. Platt Scaling & Sigmoidal Calibration:
   To ensure consistent risk semantics, raw scores are calibrated into a
   strictly bounded probability interval [0.0, 1.0]:

     R_calibrated = 1.0 / ( 1.0 + exp( - ( α * R_raw + β ) ) )

3. Mathematical Clamping Guard:
   Guarantees strict compliance with Pydantic schemas under any numerical drift:

     Final_Risk_Score = min( 1.0, max( 0.0, R_calibrated ) )

4. Decision Gate:
   - Final_Risk_Score >= 0.70  -> CRITICAL / HIGH Alert (Auto SAR trigger)
   - 0.40 <= Final_Risk_Score < 0.70 -> MEDIUM Alert (Review Queue)
   - Final_Risk_Score < 0.40   -> LOW Risk (Cleared & settled)

8. FEATURE CONTRACT (THE 9 CORE TABULAR SIGNALS)
================================================================================
Every transaction is parsed into a standardized feature contract:
1. `amount`: Monetary value of the transaction.
2. `oldbalanceOrg`: Initial balance of originating account before transfer.
3. `newbalanceOrig`: Balance of originating account after transfer.
4. `oldbalanceDest`: Initial balance of destination account before transfer.
5. `newbalanceDest`: Balance of destination account after transfer.
6. `error_orig`: Originator balance conservation discrepancy:
   `error_orig = newbalanceOrig + amount - oldbalanceOrg`
   (Non-zero values indicate accounting anomalies or artificial balance creation).
7. `error_dest`: Recipient balance conservation discrepancy:
   `error_dest = oldbalanceDest + amount - newbalanceDest`
8. `is_transfer`: Binary indicator (1.0 if type == TRANSFER, else 0.0).
9. `is_cashout`: Binary indicator (1.0 if type == CASH_OUT, else 0.0).

9. EXPLAINABLE AI (XAI) & SHAP TRANSPARENCY
================================================================================
In financial compliance, "Black-Box" AI is prohibited by regulators. Every
freezing action or SAR filing must be legally defensible.

Our platform integrates SHAP (SHapley Additive exPlanations):
- Mathematically attributes the exact contribution of each feature to the
  final risk prediction.
- Example outputs delivered in the compliance dossier:
  * `origin_balance_depleted: +0.40` (Account completely emptied)
  * `destination_balance_discrepancy: +0.20` (Recipient balance mismatch)
  * `type_TRANSFER_or_CASHOUT: +0.25` (High-risk laundering rail)
  * `iso_turnover_depth: +0.35` (Abnormal turnover velocity)
- Emits human-readable natural language rationales alongside raw numbers.

10. ENGINEERING CHALLENGES ENCOUNTERED & EXACT SOLUTIONS
================================================================================
During the development and deployment lifecycle, multiple critical engineering
hurdles were solved:

1. Challenge: Extreme Class Imbalance (0.2% Fraud Rate in PaySim)
   - Problem: Naive models achieve 99.8% accuracy simply by classifying everything
     as legitimate, missing 100% of money laundering.
   - Solution: Restricted training to actionable classes (TRANSFER and CASH_OUT),
     applied `scale_pos_weight` frequency balancing in XGBoost, and optimized
     for Precision, Recall, and AUC-ROC rather than naive accuracy.

2. Challenge: Memory Constraints in Container & Low-RAM Environments
   - Problem: Attempting to train deep models locally on millions of rows caused
     immediate Out-Of-Memory (OOM) crashes.
   - Solution: Implemented modular Google Colab GPU training pipelines, serialized
     trained weights using Joblib, and deployed lightweight binary artifacts
     into the backend for sub-15ms local CPU inference.

3. Challenge: OpenMP C++ Library Missing in Slim Docker Images
   - Problem: When running XGBoost in minimal Linux containers (`python:3.11-slim`),
     the application crashed with `OSError: libgomp.so.1: cannot open shared object`.
   - Solution: Updated both `Dockerfile` configurations to explicitly install
     `libgomp1` via `apt-get`, enabling native C++ multi-threaded tree inference.

4. Challenge: Test Suite Root Endpoint Conflict (JSON vs React SPA)
   - Problem: In unified Docker builds, FastAPI mounts the compiled React SPA
     at root (`/`). Automated Pytest tests expected a JSON greeting payload,
     causing JSONDecodeError failures.
   - Solution: Updated `test_health.py` with content-type inspection to validate
     both headless API JSON responses and production SPA HTML delivery modes.

5. Challenge: Anomaly Score Clamping Under Additive Penalties
   - Problem: Multiple concurrent anomaly signals occasionally generated raw
     scores of 1.15 to 1.35, triggering Pydantic schema validation errors.
   - Solution: Enforced strict mathematical clamping:
     `score = min(1.0, max(0.0, score))` across all plugin prediction layers.

6. Challenge: Monospace ASCII & Broken Mermaid Diagrams in Markdown
   - Problem: Markdown viewers failed to render Mermaid flowcharts and ASCII
     boxes consistently, displaying broken syntax and dotted boxes.
   - Solution: Engineered a dedicated, self-contained interactive web dashboard
     inside `diagrams/` built with 100% native HTML, CSS, and JS.
