1. PROJECT OVERVIEW & PURPOSE
--------------------------------------------------------------------------------
Project Title: Enhancing Anti-Money Laundering Detection through Machine Learning
               and Graph-Based Analytics
Development Team: AML Team
Live URL: https://anti-money-laundering.onrender.com/
API Documentation: https://anti-money-laundering.onrender.com/docs
Repository: https://github.com/BharathKumar113/anti_money_laundering

This project is a production-grade, real-time financial intelligence and AML
surveillance platform. It is engineered to identify, investigate, and prevent
financial crimes such as round-tripping, smurfing (structuring), mule account
layering, and account takeover fraud in high-throughput banking systems.

Traditional financial monitoring systems rely on static threshold rules (e.g.,
flagging any transaction greater than $10,000), which leads to two fatal flaws:
1. Skyrocketing False Positives (over 90-95%), overwhelming compliance teams.
2. Inability to detect sophisticated multi-hop fraud networks, where money is
   intentionally routed below threshold limits through chains of accounts.

Our platform solves this by implementing a Defense-in-Depth architecture that
combines five distinct detection layers:
1. Heuristic Rule Engine (Compliance baseline)
2. Supervised Machine Learning (XGBoost Classifier)
3. Unsupervised Outlier Isolation (Isolation Forest)
4. Unsupervised Deep Learning (Neural Autoencoder Reconstruction MSE)
5. Network Graph Analytics (NetworkX Directed Multigraph Cycle & Mule Detection)

Coupled with SHAP (SHapley Additive exPlanations) for algorithmic transparency,
the platform computes a unified, weighted risk score (0.0 to 1.0) and generates
auditable compliance cases for investigators.


2. THE PROBLEMS WE SOLVED & CHALLENGES FACED
--------------------------------------------------------------------------------
During research, architecture design, and deployment, several complex technical
hurdles were encountered and resolved:

* Problem 1: Extreme Class Imbalance in Financial Data
  - Challenge: In the 6.3-million-row PaySim benchmark dataset, fraudulent
    transactions account for less than 0.2% of total activity. A standard model
    simply predicts "legitimate" 99.8% of the time, producing high accuracy but
    missing virtually 100% of crimes.
  - Solution: We restricted training to high-risk transaction types (TRANSFER
    and CASH_OUT, where fraud physically occurs), applied class-frequency
    weighting (`scale_pos_weight` in XGBoost), and optimized using Precision,
    Recall, and F1-score rather than naive accuracy.

* Problem 2: Hardware Constraints on Mobile / Termux Environment
  - Challenge: The system was developed on an Android device running Termux with
    a PRoot Debian container (~1.4 GB available RAM). Attempting to train
    heavy ML models locally on millions of rows would trigger an immediate
    Out-Of-Memory (OOM) kernel crash.
  - Solution: We designed modular Colab training scripts, performed distributed
    GPU/CPU model training in Google Colab, serialized the models via Joblib,
    and transferred the lightweight binary bundles (.joblib) into the backend
    for low-latency local inference.

* Problem 3: Containerization & OpenMP System Library Missing in Docker
  - Challenge: When packaging the application into a minimal Docker container
    (`python:3.11-slim`), XGBoost failed to load with `OSError: libgomp.so.1:
    cannot open shared object file`. Additionally, `scikit-learn`, `xgboost`,
    and `joblib` were initially missing from `requirements.txt`.
  - Solution: Updated `requirements.txt` with exact version pins, and modified
    both the root `Dockerfile` and `backend/Dockerfile` to install `libgomp1`
    (the OpenMP runtime) via `apt-get`, enabling C++ accelerated tree inference
    inside headless cloud containers.

* Problem 4: Test Suite Root Endpoint Conflict (JSON vs HTML SPA)
  - Challenge: When building the unified Docker container, FastAPI mounts the
    compiled React frontend static assets (`frontend/dist/index.html`) at root
    (`/`). Existing automated unit tests expected a JSON greeting payload,
    causing JSONDecodeError during automated testing.
  - Solution: Updated `test_health.py` with content-type inspection to seamlessly
    validate both JSON API mode and SPA HTML distribution mode, ensuring a
    flawless 14/14 automated test pass rate.

* Problem 5: Anomaly Score Clamping During Database Seeding
  - Challenge: During database initialization, additive anomaly penalties from
    multiple feature mismatches occasionally pushed raw Autoencoder scores to
    1.35, triggering Pydantic schema validation errors (`risk_score <= 1.0`).
  - Solution: Enforced strict mathematical calibration and bounding:
    `anomaly_score = min(1.0, max(0.0, calibrated_score))`, ensuring guaranteed
    schema compliance across all test payloads and seed pipelines.


3. MACHINE LEARNING & DETECTION MODELS (WHAT & WHY)
--------------------------------------------------------------------------------
Our platform does not rely on a single algorithm; it uses a weighted ensemble
where each model specializes in catching a distinct category of financial crime:

1. Supervised XGBoost Classifier (`xgb_aml.joblib` ~403 KB):
   - Model Type: Gradient-Boosted Decision Trees (Supervised)
   - Why We Used It: XGBoost is the gold standard for tabular financial data.
     It captures non-linear relationships between transaction amounts, balance
     deltas, and account history with state-of-the-art accuracy.
   - What It Catches: Known laundering signatures, rapid balance depletion,
     and origin-to-destination balance discrepancies.
   - Weight in Ensemble: 1.0 (Highest weight for known patterns).

2. Unsupervised Isolation Forest (`isolation_forest.joblib` ~22 MB):
   - Model Type: Random Partition Isolation Trees (Unsupervised)
   - Why We Used It: Fraudsters frequently change tactics to avoid known rules.
     Isolation Forest isolates anomalies by randomly selecting a feature and
     splitting values. Outlier transactions require significantly fewer splits
     to isolate than normal transactions.
   - What It Catches: Extreme transactional outliers, abnormal volume spikes,
     and unusual ratio deviations without requiring prior labels.
   - Weight in Ensemble: 0.85.

3. Unsupervised Deep Autoencoder (`autoencoder.joblib` ~21 KB):
   - Model Type: Multi-Layer Perceptron Autoencoder (9 -> 16 -> 4 -> 16 -> 9)
   - Why We Used It: An autoencoder compresses 9-dimensional transaction vectors
     into a 4-dimensional latent bottleneck representation, then reconstructs
     them. Because it is trained on normal banking patterns, it cannot
     reconstruct abnormal or novel transaction structures.
   - What It Catches: Zero-day laundering techniques. A high Mean Squared Error
     (MSE) between input and reconstructed features triggers an anomaly alert.
   - Weight in Ensemble: 0.80.

4. NetworkX Graph Analytics (`graph_ring_plugin.py`):
   - Model Type: Directed Topological Graph Analysis (Graph Theory)
   - Why We Used It: Standard tabular machine learning cannot see relationships
     between multiple transactions. Criminals move money through layering chains
     (Account A -> B -> C -> A) to disguise origin.
   - What It Catches: Circular loops (round-tripping), mule fan-in / fan-out
     bursts, and high-velocity fund hops.
   - Weight in Ensemble: 0.90.

5. Heuristic Compliance Rule Engine (`rule_based_plugin.py`):
   - Model Type: Deterministic Threshold Heuristics
   - Why We Used It: Banking regulations (FATF, FinCEN, RBI) legally mandate
     deterministic checks (e.g., Currency Transaction Reports for large sums).
   - What It Catches: Hard currency thresholds (>= ₹2,00,000 / $10,000), complete
     origin account emptying, and unverified mule destination accounts.
   - Weight in Ensemble: 0.50.


4. FEATURE CONTRACT (THE 9 ENGINEERED FEATURES)
--------------------------------------------------------------------------------
All ML models adhere to a strict, standardized 9-dimensional feature contract:

1. `amount`: Transaction monetary value.
2. `oldbalanceOrg`: Initial balance of originating account before transfer.
3. `newbalanceOrig`: Balance of originating account after transfer.
4. `oldbalanceDest`: Initial balance of recipient account before transfer.
5. `newbalanceDest`: Balance of recipient account after transfer.
6. `error_orig`: Originator balance conservation discrepancy:
   `error_orig = newbalanceOrig + amount - oldbalanceOrg`
   (Non-zero values indicate accounting anomalies or artificial inflation).
7. `error_dest`: Recipient balance conservation discrepancy:
   `error_dest = oldbalanceDest + amount - newbalanceDest`
8. `is_transfer`: Binary flag (1.0 if transaction type is TRANSFER, else 0.0).
9. `is_cashout`: Binary flag (1.0 if transaction type is CASH_OUT, else 0.0).


5. EXPLAINABLE AI (XAI) & SHAP EXPLANATIONS
--------------------------------------------------------------------------------
In regulated financial institutions, "Black-Box" AI is prohibited. Regulators
mandate that any transaction freeze or Suspicious Activity Report (SAR) must be
justified with clear, human-understandable evidence.

Our system incorporates SHAP (SHapley Additive exPlanations):
- Every prediction outputs mathematical attributions showing how much each
  individual feature pushed the risk score up or down.
- Examples of generated explainability outputs:
  * `origin_balance_depleted: +0.40`: Origin account drained to zero.
  * `destination_balance_discrepancy: +0.20`: Recipient balance mismatch.
  * `type_TRANSFER_or_CASHOUT: +0.25`: High-risk laundering mechanism.
  * `iso_turnover_depth: +0.35`: Entire account balance moved in single transaction.
- In addition to mathematical weights, each plugin emits natural language
  reasons (e.g., "Latent representation error: balance shift divergence").

7. BACKEND ARCHITECTURE & DESIGN PATTERNS
--------------------------------------------------------------------------------
1. Dynamic Plugin Registry Pattern (`backend/app/ml_plugins/`):
   - Decoupled architecture where every model is an independent plugin.
   - Inherits from `BaseAMLModelPlugin`.
   - Models can be enabled, disabled, or have their weights rebalanced at
     runtime via REST API (`/api/v1/plugins/`) without restarting the server.
   - All plugins proudly report author: "AML Team".

2. Automated Compliance Triage & Alert Pipeline (`backend/app/services/aml_service.py`):
   - Every transaction is evaluated through the ensemble in under 15ms.
   - If the combined risk score >= 0.70: An automated CRITICAL/HIGH Alert is
     instantly created in the database with status `PENDING`.
   - If the combined risk score is between 0.40 and 0.69: A MEDIUM Alert is raised.
   - Transactions below 0.40 are cleared as LOW risk.
   - Investigators can assign cases, update investigation notes, and resolve alerts
     directly from the investigator dashboard.

3. Graph Forensics Engine (`backend/app/services/graph_service.py`):
   - Construct directed money transfer networks on the fly.
   - `/api/v1/graph/account/{account_id}`: Returns multi-hop subgraphs for visual
     investigations.
   - `/api/v1/graph/cycles`: Runs global cycle detection (2 to 5 hops) to catch
     layering rings (e.g. Account A -> Account B -> Account C -> Account A).
